# v1.0.0 Release Cut Plan

> **Status**: done, 2026-09-12 — all six steps landed; v1.0.0 is cut. v0.6.4 shipped the maintenance backlog (its publish run
> was blocked by the Trivy gate; v0.6.5 followed with the Alpine package
> upgrade), ADR-0018 decided T7, the firmware-cache and failed-check defects
> are fixed, and the documentation pass landed the upgrade path and the
> Known Issues list. **Target**: after `v0.6.4` ships the
> maintenance backlog. **Type**: promise, not payload — the release that
> freezes the API contract. **Backwards-compat window**: opens here.

Unlike `v0.3.0`, this cut carries no breaking change and, if the
sequence below is followed, almost no code. What it ships is a
**guarantee**, and the work is making sure the guarantee is true before
it is made.

---

## The premise: behaviour is already frozen

Measured 2026-09-12, not assumed:

```bash
git diff --stat v0.6.3..main -- internal/ cmd/ web/src/   # empty
git rev-list --count v0.6.3..main                          # 45
```

Since `v0.6.3` (2026-07-23) not one line of backend or SPA source has
changed. All 45 commits are dependencies, CI, docs, and memory. The
roadmap called this in May — "largely field-driven from here, the core
feature set is complete for a single-operator trusted-LAN deployment" —
and seven weeks of field use have produced maintenance, not features.

That is the actual argument for 1.0. Not maturity as a feeling: a
codebase that has stopped changing shape is one whose shape can be
promised.

## Gate items (from [roadmap.md](../roadmap.md) § v1.0.0 Gate)

The roadmap names exactly two. Both are documentation.

### 1. API stability guarantee

The policy text already exists in
[ARCHITECTURE.md § API Versioning Policy](../ARCHITECTURE.md) and only
needs its tense changed from "when v1.0 lands, the policy hardens to"
into the active rule. **But it cannot be activated as written** — see
the T7 decision below.

### 2. Documented upgrade path `v0.6.x → v1.0.0`

With no breaking change, this is short and should say so plainly: pull
the new image, recreate the stack, no migration, no config change, no
data-format change. Worth writing anyway — an upgrade doc that says
"nothing to do" is a promise too, and its absence reads like an
oversight rather than a statement.

Migrations are the one thing to re-verify before publishing it: confirm
that the migration set applied by `v1.0.0` is byte-identical to
`v0.6.3`'s, so the claim is checked rather than assumed.

## The decision that must happen first: T7

**The written policy describes an API that does not exist.** It promises
that "`/api/v1/*` stays stable" and that breaking changes ship under
`/api/v2/`. The server serves **52 routes under an unversioned
`/api/*`**; the only `v1` in the tree is the OpenAPI document's own path
(`/api/openapi/v1.json`) and the spec's `info.version` field.

Shipping 1.0 without resolving this publishes a stability guarantee
whose subject is fictional. Two honest ways out:

**(a) Mount the prefix.** Move all 52 routes to `/api/v1/*`, keep
`/api/*` as an alias for one release line with a `Deprecation: true`
header, update the SPA client ([web/src/lib/api.ts](../../web/src/lib/api.ts))
and the `shellyctl` CLI base path. Cost: real but bounded — one router
change, one client constant, the E2E suite proves it. This is the last
moment it is free; after 1.0 the alias becomes a permanent obligation.

**(b) Declare `/api/*` the stable surface.** Rewrite the policy to name
the unversioned prefix, and reserve `/api/v2/*` as the *future*
breaking-change namespace. Cost: zero code, one paragraph. Slightly
unusual shape, entirely defensible for a single-operator LAN tool whose
clients are the bundled SPA, `shellyctl`, and MCP.

**Recommendation: (b).** The roadmap's own verdict on T7 — "pure
plumbing with no payoff until a breaking `/api/v2` exists" — is right,
and 1.0 does not change it. What 1.0 changes is that the *policy text*
must stop describing a prefix nobody serves. Option (b) makes the
document true at the cost of a paragraph; option (a) makes it true at
the cost of touching every route, every client, and every operator's
ad-hoc scripts, to buy a namespace that may never be needed.

Either way: **write it as an ADR.** This is the single architectural
decision of the release, and ADR-0001…0017 set the precedent.

## Known field defects — fix or name, do not ignore

Three defects are documented in [CLAUDE.md](../../CLAUDE.md) and none is
fixed. A 1.0 that silently carries them is worse than one that lists
them.

| Defect | Disposition |
| --- | --- |
| **FW-cache blanking**: any fleet-wide `UpsertDevices` (normally via `ConfirmScan`) discards `FWAutoUpdate` / `FWCheckedAt` / `FWAvailableStable` / `FWAvailableBeta`, because a scan probe does not carry them. Measured: 44× `stable` → 43× empty. | **Fix before 1.0.** The seam is known and narrow — carry the four `FW*` fields over from the existing row in [internal/db/devices.go](../../internal/db/devices.go), exactly as `DeviceNum` and `FirstSeen` already are. Cheapest of the three and the only one that destroys state. |
| **Stale device IP**: the row's `ip` is written only by a scan, so a moved DHCP lease leaves jobs talking to the wrong host while `/api/devices` still reports `online: true` with an empty `last_refresh_error`. | **Fix if cheap, else name.** The suggested seam is re-resolving the mDNS name on a connection-level failure before declaring a device unreachable. If that grows past a small diff, it belongs in Known Issues instead — it is a correctness wart, not data loss. |
| **`shelly-hz2` missed by the subnet scan** while answering `/shelly` in 30 ms; its wired twin `hz1` is found every sweep. Cause unknown; the Ethernet-only hypothesis is ruled out. | **Name it.** Do not hold 1.0 for an unexplained single-device discovery miss, and do not guess at a fix — this repo has a documented history of exactly that going wrong (the OTA `premature end of data` retraction). Known Issues, with the ruled-out branch recorded so nobody re-walks it. |

## Sequence

1. **`v0.6.4` — maintenance cut.** Ship the seven weeks of deps, CI and
   docs that are sitting in `[Unreleased]`. Purpose: make the 1.0 diff
   contain *only* the promise. A release whose changelog mixes "we now
   guarantee the API" with "bumped brace-expansion" undersells both.
2. **T7 ADR** (ADR-0018). Decide (a) or (b); harden the policy text in
   ARCHITECTURE.md to match the decision.
3. **FW-cache fix** + tests, own PR.
4. **Stale-IP**: attempt the mDNS re-resolve; time-box it. Whatever is
   left goes to Known Issues.
5. **Docs pass**: upgrade path `v0.6.x → v1.0.0`; Known Issues section;
   roadmap "Now" is stale (still claims `v0.5.x` / "production tracks
   v0.5.2", four releases behind) and the § v1.0.0 Gate becomes the
   release's own checklist.
6. **Cut `v1.0.0`** per the standing convention in
   [DEVELOPMENT.md § Release Cadence Convention](../DEVELOPMENT.md):
   `VERSION` + `web/package.json` + lockfile bumped together,
   lightweight tag, `git push origin main v1.0.0` (a lightweight tag is
   not carried by `--follow-tags`), CHANGELOG header
   `## [1.0.0] - YYYY-MM-DD — em-dash subtitle` because the
   publish-image workflow lifts that subtitle into the GitHub Release
   title.

Steps 2–4 are independent and can land in any order; only step 1 must
precede and step 6 must follow.

## Explicitly not in this cut

- **No feature work.** If something wants building, it wants a `v1.1`.
- **No `/api/v2`.** The namespace is reserved by the policy, not opened.
- **No re-litigation of the ADR-0001 non-goals** (multi-user RBAC, WAN
  exposure, HA/clustering, self-healing). 1.0 is a promise about the
  scope that exists, not an invitation to widen it.
- **No dependency-tree surgery.** Issue #13 (`mongo-driver` linked via
  gin's BSON binding) stays open and stays accepted: verified
  2026-09-12 that the tree imports `gin-gonic/gin/binding` nowhere and
  contains no `c.Bind*` call at all — every handler decodes through
  `decodeJSON` with `http.MaxBytesReader`. The driver is linked but
  unreachable, and gin ships no build tag to drop it (`nomsgpack` has
  no `nobson` counterpart). Note it in Known Issues, do not fork gin
  for it.
